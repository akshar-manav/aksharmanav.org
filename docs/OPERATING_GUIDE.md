# Operating guide

## Purpose

This guide keeps the website project understandable across contributors, tools and future working sessions. It is deliberately small. Decisions that affect product direction, truth, architecture, security or releases must be recorded in the repository.

## Working principles

1. Organisational truth comes before persuasive copy.
2. Product, brand, design and engineering decisions are documented separately when the distinction matters.
3. Security, privacy, accessibility and recoverability are release requirements.
4. Changes are made through reviewable branches and pull requests.
5. Production is updated only from an accepted, tagged release.
6. Authentic organisational material is preferred; stock imagery is excluded.
7. Multilingual capability is designed into the content model from the beginning.
8. The system should remain portable and inexpensive to operate.

## Authority and participation

- **Product owner and final website release authority:** Ajinkya Kinhikar.
- Contributors may propose, write, translate, review, test and maintain.
- Discussion and deliberation should be open, respectful and recorded when consequential.
- Official philosophical, historical, governance or organisational claims require authorised review.
- Production credentials and deployment authority are restricted even when source code is public.
- This project-level release authority does not prevent Akshar Manav from developing broader democratic and decentralised governance.

## Sources of truth

Use sources in this order:

1. verified legal and organisational records;
2. approved canonical organisational documents;
3. explicit clarifications from the current release authority;
4. historical publications and archives, with their date and context preserved;
5. existing websites and social posts;
6. drafts and AI-generated interpretations.

Lower-ranked material must not silently override higher-ranked material.

## Minimal durable records

Maintain:

- the product brief;
- the organisational truth register;
- architecture and release records;
- a short backlog;
- dated run records for consequential work.

Avoid creating documents that have no active owner or practical use.

## Change flow

```text
issue or scoped task → working branch → checks → draft PR → review → acceptance → merge
```

Deployment follows the separate release process. No merge or deployment is implied merely because a draft PR exists.
